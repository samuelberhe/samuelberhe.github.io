Wiz project architecture · proposed · v2

Four roots and a
service catalog. One asset,
three lenses.

A Wiz project has exactly one parent. That single constraint is why policy scope and developer access cannot share a hierarchy — so build disjoint project trees over overlapping assets: two for Humana, two more for subsidiaries as top-level peers rather than children. The Service Catalog carries the per-APPSVC granularity that would otherwise explode your project count.

Read it from one asset outward

Every asset lands in exactly one policy leaf, exactly one team project, and exactly one service. Nothing else in this design matters if that sentence stops being true.

Humana · two roots

Tree 1 is shaped by enforcement boundaries. Tree 2 is shaped by the org chart. They share no project objects — only assets. Neither tree is allowed to do the other's job. Subsidiaries appear in neither; they get their own pair of roots below.

Where SSO actually lands. Nobody logs into a project. SSO authenticates the user once at the tenant (Entra → SAML/OIDC), and the IdP group claim maps to a Wiz role scoped to a project. One Entra group per team project, granting a scoped Member role. Grant on the dept-* folder instead and the user gets every team beneath it — that is the Business Area lead role, not the developer one.
Projects do not contain resources. A project is a saved scope, not a bucket. Nothing is ever placed into dha-group-medicare by hand — it resolves to whatever currently matches its APPSVC tag query across cloud, repos, registries and namespaces. Add a resource with the right tag tomorrow and it appears; retag it and it moves.
RBAC binds here and nowhere else. Each team project unions that team's APPSVCs across cloud, code, registry and Kubernetes, so a developer sees their whole stack in one place — and nothing else. Entra group → SCIM → project role, sourced from the same CMDB record that defines membership.
Do not add an environment layer here. Team × environment is a combinatorial trap. Developers filter by the environment value already set on Tree 1's links.

Service Catalog · spans both trees

Ownership & routing

This is the piece that keeps Tree 2 shallow. One service per APPSVC, auto-discovered from humana-resource-id tags plus Helm and ArgoCD metadata. Services are not bound by the project hierarchy, so a single service can reach across a policy leaf, a team project, a repo and a namespace at once — which is exactly what an application actually is.

Tag coverage

a report, not a project

With no unowned project in the tree, coverage still has to live somewhere or it stops being anyone's problem. Make it a saved query plus a weekly report: assets in a Tree 1 leaf that resolve to no service and no team project.

This is the highest-risk dependency in the design. Everything on the access side is a tag query, so an asset missing humana-resource-id is invisible to every developer and to every service — silently. If coverage is below roughly 95%, fix tagging at the landing zone with a deny-untagged policy before opening self-service.

Subsidiaries · two more roots

Not nested under Humana. Peers to it, at the top level, mirroring the same pattern so nothing new has to be learned — but with their own policy baseline, their own IdP, and their own admins. Each subsidiary is a folder inside these roots, which is what makes a divestiture a clean lift rather than an excavation.

Own SSO, own APPSVC namespace. If a subsidiary does not use humana-resource-id, it needs its own discovery rule for the Service Catalog. Do not force their tags into Humana's convention just to make one query work.
Folders are not isolation. A separate root makes the boundary legible and easy to audit. It does not make the data legally segregated. If that is the requirement, the answer is a separate tenant — see the open question below.

Service discovery needs its own rule here. Wiz can discover services from tags, Helm charts or ArgoCD apps. With no ownership tag, subsidiary services come from Helm/ArgoCD metadata, repo ownership, or a manual definition per account.

Rules that keep it from rotting

The structure survives a reorg. The discipline is what usually doesn't — write these down and enforce them in review.

Scoping

Controls target Tree 1 only

Never scope a control to an ownership project. Team membership drifts as people move, and enforcement coverage would fall away silently.

Rollout

Canary, then widen

Every new control follows one path: azohp-policytest or a single ADO project → whole non-prod → prod. The structure supports it; make it the ritual.

Reporting

Never sum across trees

An asset lives in both, so totals double. Tree 1 is the record for compliance and coverage. Tree 2 is the record for remediation and SLA. Put that in the dashboard titles.

Provisioning

Nothing is hand-created

Both trees are generated from the CMDB via wiz_project Terraform and reconciled nightly. Pin the provider version and keep a GraphQL fallback — it is community-maintained, not shipped by Wiz.

Naming

The picker is flat

Folders nest; the search box does not. Leaf project names carry their own path: gcp3-humins-prod, az-prod-humv2, dha-group-medicare, svc-app0000646-….

Attributes

Criticality lives in Tree 1

HBI/MBI/LBI belongs on stable enforcement leaves. Ownership projects churn with every reorg, and business impact should not churn with them.

Build order

Genuinely sequential — each step is load-bearing for the next. The long pole is first, and it is not a Wiz problem.

1

Tag coverage and repo ownership mapping

Cloud resources carry APPSVC tags. Repos do not — you need GitHub custom properties, CODEOWNERS, or a repo→APPSVC table. Namespaces use labels; images resolve through code-to-cloud lineage. This is the hardest engineering work here and it gates everything downstream.

2

Tree 1 in Terraform

Gap-free, mutually exclusive, with environment and business_impact set on every link. Prove coverage by asserting that unassigned asset count equals the unowned project count. Stand up the subsidiary policy root in the same pass, with its own baseline.

3

Migrate controls onto Tree 1 leaves

Retire every ad-hoc scope. From this point the answer to “where does this rule apply” is always a project name.

4

Turn on Service Catalog discovery

Review suggested services, accept them, assign owners from the CMDB. Do not treat it as an inventory exercise — the value is the owner field.

5

Tree 2, piloted with one team

Generated from the CMDB. Pick a team that will tell you honestly when their view is wrong, and do not scale until it is right. This is the gate that decides whether developers trust the platform.

6

Route issues by service owner, then open self-service

Tickets land in the right queue automatically. Only then announce it broadly.

Three answers you need before you build

Each of these changes the design if the answer goes the wrong way. Get them settled first.

Is environment separated by org node in gcp1, AWS and OCI?

AZOHP management groups already give you a clean prod/non-prod boundary. If AWS accounts or the gcp1 legacy estate mix environments, your “Azure prod only” rule works and your “AWS prod only” rule leaks — and tags will not save you.

Ask: cloud platform team, per provider

What is the authoritative repo → APPSVC mapping?

Tree 2 and the Service Catalog both assume every repo resolves to a team. Across three EMU orgs plus ADO, that mapping has to exist somewhere and be maintained. If it doesn't exist yet, step 1 is longer than it looks.

Ask: EMU org admins + CMDB owner

Separate roots, or a separate tenant?

Roots 3 and 4 make the boundary legible and auditable, and they make a divestiture a lift rather than an excavation. What they do not do is segregate the data — a Humana global admin still sees everything. If the requirement is legal segregation rather than tidy separation, only a separate tenant satisfies it, and retrofitting that after go-live is brutal.

Ask: legal and M&A, before step 2
